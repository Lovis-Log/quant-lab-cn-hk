# 时区与交易时段（Time Zone and Trading Session）

## 快速理解

### 一句话解释

时间里有两个完全不同的东西：价格对应的“交易日”和本机收到数据的“接收时刻”；Quant Lab 把接收时刻按 UTC 记录、按北京时间显示，但不提供交易所的盘中报价时钟或交易时段模型。

### 它解决什么问题

它让数据来源、缓存年龄、自动刷新和实验档案有一个明确的时间参照，避免把“页面重绘时间”“本机接收时间”和“交易所报价时间”混为一件事。

### 最常见的误解

- **“接收时间就是行情时间”**：`received_at` 只表示本机拿到响应的时刻；行情日期是价格对应的交易日，确切延迟未知。
- **“日期字段带时间”**：历史日线的 `date` 是日期，不是带时区的报价时间戳。
- **“北京时间就是交易所时间”**：A 股和港股目前都在 UTC+8，但“同一时区”不等于“同一交易时段”或“同一报价时刻”。
- **“所有市场都适用同一交易时段”**：不同市场、不同产品、半日市和特殊安排的时段不同。
- **“历史日线有盘中时间”**：日线只给交易日，不提供开盘/收盘的精确时刻。

## 软件实践

### 在 Quant Lab 哪里出现

- 行情 `received_at`：本机收到上游响应的时间，存 UTC。
- 数据更新状态：上次成功获取时间、下次尝试时间，按北京时间 `UTC+08:00` 显示。
- 左侧历史区间默认值和快照读取结束日期：使用 `Asia/Shanghai` 的当天日期。
- 研究实验档案：保存 `received_at`，报告按北京时间显示。
- 名称/目录缓存：保存成功获取时间，页面显示北京时间。

### 输入、输出和单位

- 输入：上游响应时间、本机时钟、日期选择。
- 输出：UTC 时间戳（存储/内部）、北京时间字符串（展示）、日期（行情/区间）。
- 时间戳是“时刻”，日期是“日”；二者不能直接相减当作交易日数。
- `received_at = None` 时显示“未记录（不能推断为当前时间）”，不能补成当前时间。

### 结果应该怎么读

- 先区分“行情日期”和“上次成功获取时间”：前者是价格对应的交易日，后者是本机拿到响应的时间。
- 再把“接收时间”和“缓存年龄”区分开：缓存年龄是距离上次成功获取的时间，不是行情延迟。
- 看到“北京时间 09:30”时，不要自动认为这是交易所开盘报价；它可能只是本机在 09:30 收到了某条响应。
- 需要比较两个数据批次时，使用同一时区显示的时间戳，并保留原始 UTC 记录。

### 当前软件边界

**软件已经计算或显示什么**

- 将 `received_at` 按 UTC 存储，按北京时间 `UTC+08:00` 显示。
- 显示行情日期、上次成功获取时间、缓存年龄、下次尝试时间和最近更新结果。
- 使用 `Asia/Shanghai` 的当天日期作为历史区间默认结束日和快照读取结束日。
- 在实验档案和 Markdown 报告中保留/显示接收时间。

**软件只间接使用什么**

- 自动刷新间隔、缓存 TTL、5 秒防抖和 1 秒快照请求间隔使用本机时钟/单调时钟，不是交易所时段。
- 历史区间默认值、最近 21 天快照窗口和“今天”的判断依赖本地日期。
- 研究档案的 `created_at` 使用 UTC；报告中的实验时间可能另行显示。
- 文件日志和数据库时间戳用于排查，不用于判断行情新鲜度。

**软件没有提供或没有建模什么**

- 交易所报价时间、逐笔时间戳、开盘/收盘精确时刻。
- 交易时段、集合竞价、午休、盘前/盘后、半日市和临时休市。
- 不同市场的时区/夏令时规则；当前只按 `Asia/Shanghai` 显示北京时间。
- 行情延迟、网络延迟、数据源时间戳和交易所时钟偏差。
- 实时行情时钟、市场状态或“当前是否开市”的判断。

**核验状态**：

时区数据库、交易所时段和休市安排会变化；本文只描述当前软件的时间戳与显示行为，不声明覆盖交易所全部时段规则。相关规则标记 NEEDS_REVIEW（核验日期：2026-10-22）。

## 专业原理

### 正式定义

- **UTC**：协调世界时，作为跨时区存储和传输的统一时间基准。
- **本地时间**：某个时区下的墙上时间，例如北京时间 `UTC+08:00`。
- **交易所时间**：交易所规定的交易时段和报价时间，通常以交易所当地时区表示。
- **交易日**：价格对应的日期，只有日期，没有盘中时刻。
- **接收时刻**：本机收到数据的时间戳，表示“何时拿到响应”，不表示“交易所何时成交”。

### 公式与符号

北京时间与 UTC 的固定换算（中国标准时间，当前无夏令时）：

`t_Beijing = t_UTC + 8 小时`

一般时区换算：

`t_local = t_UTC + offset(zone, t_UTC)`

其中 `offset` 可能随夏令时变化；不能对所有市场都硬编码 `+8`。日期与时间戳的关系：

`observation_date = date(价格对应的交易日)`

`received_at = timestamp(本机收到响应的时刻)`

二者不是同一个量，不能相减得到“行情延迟”。

### 可手算的小例子

假设某次响应在 UTC `2026-10-22 01:30:00` 到达本机：

- 北京时间 = `2026-10-22 09:30:00 UTC+08:00`。
- 如果该响应里最新日线的 `date` 是 `2026-10-21`，那么：
  - 行情日期 = `2026-10-21`；
  - 接收时间 = `2026-10-22 09:30`（北京时间）；
  - 不能写成“行情在 09:30 更新”或“报价时间是 09:30”。
- 若上次成功获取时间是北京时间 `09:25:00`，当前是 `09:30:00`，缓存年龄 = 300 秒；这 300 秒是“距上次成功获取”的时间，不是行情延迟。
- 若某市场在 09:30 开盘，09:30 收到响应也不证明响应里的价格是 09:30 的成交价；日线只有交易日，没有盘中时刻。

另一个例子：UTC `2026-10-21 16:30` 对应北京时间 `2026-10-22 00:30`；日期已经跨日。如果只看“00:30”而不看时区，容易把交易日和接收日混在一起。

### 前提假设

- 本机时钟基本准确；`received_at` 来自本机，不是交易所授时。
- 北京时间显示使用 `Asia/Shanghai`；中国当前不实行夏令时。
- 历史日线的 `date` 是日期，不含时刻；不假设它能还原盘中报价。
- 交易时段、半日市和交易所时区需要另行查官方规则，不能从日线推断。

### 边界情况

- `received_at` 缺失或为 `None`；不能推断为当前时间。
- 时间戳无时区（naive）；程序按 UTC 解释，可能导致显示偏差。
- 跨日、跨月、跨年；UTC 与北京时间日期不同。
- 夏令时地区；不能硬编码 `+8`。
- 交易所临时休市、半日市、盘前/盘后交易。
- 本机时钟错误、网络延迟、缓存读取与上游响应混淆。
